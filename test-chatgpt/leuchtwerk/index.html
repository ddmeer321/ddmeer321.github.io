Warum diese Komplexität technisch Sinn ergibt

UI → FIFO → RPC → Worker → Reservierung → Animation → Commit → Journal. Mehrfachklicks werden nacheinander abgearbeitet. Die Warteschlange ist auf vier wartende Aufträge begrenzt.

Ein Blob-Web-Worker besitzt den Transaktionszustand. Korrelations-IDs ordnen Antworten zu. Bei Timeout wird dieselbe Nachricht höchstens zweimal erneut gesendet; ein begrenzter Antwortcache verhindert die erneute Ausführung. Das Fehlerlabor verwirft eine Antwort erst nach der Verarbeitung.

Eine 5-Sekunden-Lease und eine Versionsprüfung schützen die Reservierung. Bei Abbruch wird die Animation gestoppt und die Reservierung freigegeben. Der Commit ist innerhalb eines Worker-Nachrichtenhandlers atomar. UI und Worker bilden jedoch keine gemeinsame ACID-Transaktion: Bereits sichtbares Licht lässt sich nicht rückgängig machen.

Die Animation läuft über die Web Animations API. 800 ms sind die Soll-Dauer, keine Echtzeitgarantie. Beim Verlassen des sichtbaren Tabs werden aktive Animationen und wartende Aufträge abgebrochen. Während eines bereits gestarteten Commits wird dessen Ergebnis noch abgeglichen.

Die Lichtlogik läuft lokal in diesem Tab. Die vorgeschaltete Zugriffsprüfung verwendet die bestehende Anmeldung der Spielebibliothek. Worker-Transaktionen und Zähler starten nach Neuladen neu. Das begrenzte Journal wird nach Möglichkeit in localStorage gespeichert und lässt sich als JSON exportieren; es ist ein Diagnoseprotokoll, kein manipulationssicheres Audit-Archiv. Es gibt absichtlich keine automatische Wiederholung von Lichtsignalen nach einem Neustart.
